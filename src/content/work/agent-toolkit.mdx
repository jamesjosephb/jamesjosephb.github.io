## Out of the box, the assistant lacked context

Our platform is many services and front ends, each in its own repository, in a regulated financial domain. Out of the box, an AI coding assistant sees one file or one repository at a time. It knows nothing about our standards, can’t see production logs, and has no idea how the services connect.

The approach was to onboard the model the way we onboard a new engineer: an accurate map of the system, written standards, the right tools, and clear limits on what it may do without approval.

## Four layers, each with one job

The main design decision for each piece was which layer it belongs in. **Instructions** hold standards. **Skills** hold repeatable procedures. **Agents** combine them to do a whole job. **Scripts** do the parts that should give the same answer every time. Beside them sit a short **context doc** for each service and a **repo memory** of decisions and gotchas, so neither people nor agents have to rediscover them.

<ArchitectureDiagram />

All of it is versioned in a git repository of its own. A file watcher commits each change after a scan for secrets, so there is a full history of what every agent was told. The examples below are rewritten for a fictional demo app, “Fourteener Transfers”, so no internal code is shown.

# Code reviewer

You review one pull request in the Fourteener Transfers repo. You do not edit files.

## Before you start
1. Read `docs/context/<service>.md` for every service the diff touches.
2. Read `.memory/repo-memory.md` for known gotchas.

## What to check
- Money: amounts are `decimal`, never `double`, and rounding is explicit.
- Time: cut-offs are compared in business time (America/Denver), never in UTC.
- Logging: new code logs event names with the correlation ID; clients get a code, not a message.
- Tests: a behaviour change without a test is a **should-fix**.

## Output
Group findings as **Blocking**, **Should fix** and **Nit**. For each: file and line, what is wrong,
why it matters, and a suggested change. Quote the code. If you're unsure, say what would settle it.
Never approve or merge the pull request.

# Log root cause

## Steps
1. Read `docs/context/services.md` to find which services and log sources handle the request.
2. Run `trace_correlation_id` (fourteener-logs MCP server). Sort events by time.
3. Build a timeline: UTC and business time, service, event, level, one-line summary.
4. For the first warning or error, find the code that logged it, then follow the call back
   to the decision that caused it.
5. Check what changed: `git log` on those files since the last known-good release.
6. Write the report. Every claim links to a log query, a file and line, or a commit.

## Rules
- Read only. Don't edit code, replay requests or touch any environment.
- Say how sure you are and what you did not check.
- Stop after the report. A person decides what happens next.

# Security (C#)

- Access control: every endpoint declares its authorization policy. No anonymous writes.
- Injection: no string-built queries or commands. Use parameters.
- Logging: log event names and IDs. Never log names, tokens or full account numbers.
- Errors: clients get an error code and the correlation ID, never a stack trace.
- Secrets: nothing in code or appsettings files. Read them from configuration at runtime.
- Dependencies: a new or upgraded package must pass `scripts/ready.ps1` first.

If a change would break one of these rules, stop and say which rule and why instead of writing it.

## Scripts own the facts, the model owns the judgement

A model that reviews code can cite a file that is not in the diff, or a line number that does not exist. Asking it to be careful does not fix that, so the toolkit does not depend on it. The code-review agent, the pull-request triage agent and the audit of the setup itself all run the same four-step pipeline.

<CheckedOutputDiagram />

1. **Gather.** A script collects the ground truth as JSON: the commits, the changed files and line ranges, the review threads and the build results. No model is involved.
2. **Author.** The model reads the facts and the code, then writes its findings as structured data, not prose. Every finding has to cite a file and line, a commit or a review thread.
3. **Render.** A script turns the findings into the report. The script fixes the format, so two runs look the same.
4. **Validate.** In strict mode the renderer rejects any file, line, commit, thread or number that is not in the gathered facts. A rejected run fails and says why. It does not write a report with the bad finding quietly removed.

The split is deliberate. Scripts own facts and format, where the answer should be the same every time. The model owns judgement: whether a change is risky, what a review comment is really asking, which finding matters most. An invented citation cannot reach a reader, so a reviewer only has to judge the reasoning.

## Guardrails and verification

Guardrails are what made the team willing to adopt the toolkit. Every generated change follows security instructions based on the OWASP Top 10. Those rules cover the model too: its output is treated as untrusted input, the same as text from a user or a log. New or upgraded packages go through a dependency preflight. Generated files follow the same rules as hand-written ones. And nothing irreversible happens without a person saying yes.

<MayMayNot />

The table is written down as an instruction file that every agent follows. The demo version:

```md title=".github/instructions/safe-actions.instructions.md" wrap {14} {21-22}
---
applyTo: '**'
description: What an agent may do on its own, and what needs a person's approval.
---

# Safe actions

You may, without asking:
- read code, docs, logs and tickets
- run builds, tests and the read-only scripts in `scripts/`
- create a local branch and commit to it
- draft text: PR descriptions, review notes, ticket updates, replies

You must stop and ask first, every time:
- `git push`, opening or merging a pull request, deleting a branch
- changing a ticket's status or assignee
- sending or posting anything a person will read
- adding or upgrading a package
- anything that touches an environment beyond your local machine

When you stop, show exactly what you are about to do (the command, the diff, the text)
and wait for a clear yes. A yes covers that one action only.
```

### How the approval rule is enforced

A rule in a prompt is a request. These are the checks behind it.

- **Dry run by default.** An agent that can push or post first shows exactly what it would do. Doing it takes a separate, explicit yes.
- **One approval, one action.** There is no approve-everything option.
- **Approval is tied to what was reviewed.** A yes names the commit it was given for. If the branch has moved since, the approval no longer applies.
- **A staleness check before posting.** Before a reply or a review is posted, the agent checks that the pull request has not changed since the facts were gathered.
- **Automation works in its own copies.** Agents that sweep many repositories use their own clones and detached worktrees, so they never touch a developer’s working copy.
- **A preflight that fails closed.** Each run first probes what it depends on. If something is only partly available, the run stops and says so. It does not continue and return a thinner result that looks complete.

Model output is not deterministic, so the design relies on output being easy to verify rather than always correct:

- **Evidence over assertions.** Every finding or root cause links to a log query, a file and line, or a commit. For the pipeline agents, a script checks those links.
- **Scripts for anything that should be repeatable.** Builds, test runs, dependency checks and digests are scripts, not prompts.
- **People review the output.** Agent work goes through the same pull-request review as anyone else’s.

## Auditing the setup against real use

Instructions and skills are easy to add and hard to remove, and each one costs context on every run. I built an audit that reads my own session history (tool calls, failures, retry loops, context compactions and token cost) and compares it with the inventory of instructions, skills and agents. It reports what goes unused, what fails often and what costs the most, and it recommends changes.

The audit runs through the same validated pipeline, so every number in its report is checked against the gathered data. A decision ledger records the recommendations I declined, so they do not come back on the next run.

### Context is a budget

- **References load when needed.** A skill’s long reference files are read when a step needs them, not at the start.
- **Tools return briefs, not dumps.** The log-trace parser reduces a wide log export to an ordered timeline of hops and a short brief. The brief stays the same size however large the trace is.
- **Save, then parse.** Large pages and exports are saved to disk and parsed by a script, in place of the model reading them through a browser.
- **Budgets are enforced in code.** The tool that tells one session what other sessions changed has a fixed budget for each level of detail.
