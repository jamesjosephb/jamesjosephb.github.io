## The mountain is the opponent

Trailhead is an off-road driving game I’m building in Godot 4. You drive a lifted, 4Runner-inspired off-road SUV up mountain and desert trails. There are three timed destinations, an alpine summit, a glacier lake and a desert arch, each with green, blue and black routes, and an open-world Explore mode with a generated trail network and a GPS.

Getting up a trail is about reading the ground, choosing a line and a drivetrain setting, and arriving at a loose climb with enough speed, without rolling the truck. Everything in the game is generated by code when it loads: terrain, roads, trees, rocks, water, the truck itself, the sky and weather, and every sound. The repository contains no imported models, textures or audio files.

It is also an experiment in the work I do professionally. I designed and directed the game, and it was built with Claude Code, an AI coding agent, working under a harness I set up. [How that harness works](#a-harness-for-a-long-running-coding-agent) is the first of the engineering details below.

## Where it stands

- **The timed game is complete.** Title screen, level select, three levels with three routes each, medals, Expedition and Time Trial modes, results, saves, settings, keyboard and gamepad.
- **Explore mode is in progress.** A streamed 6 × 6 km open world that holds all three timed maps, with a generated trail network, GPS routing, camps, viewpoints, fords and bridges. The newest work, still on a branch, grows the world and redesigns one of the levels.
- **Next on the roadmap:** a winch and camping, random events, more weather and wildlife, then a final pass on look and performance.
- **Not released.** It runs on Windows from the Godot editor. There is no public build yet, and the repository is private.

## A harness for a long-running coding agent

Of those 747 commits, 720 were co-authored by Claude Code. The interesting part is not the volume but the rules that kept an agent working for days at a time without drifting. The history shows three phases.

**A parallel build behind contracts.** The second commit stubs every module behind stable data contracts, with an ownership table that gives each subsystem its own files. Eight modules (terrain, scatter, environment, physics, truck model, camera, audio and UI) were then built on separate branches, each in its own git worktree, and merged within about a minute of each other.

**A long-running agent on a gated roadmap.** I approved a written roadmap with milestones, performance budgets and a “won’t have” list. Its rules:

- **A feature list the agent can only mark as passing.** Each of 97 features has acceptance criteria and a command that verifies it. The agent may change only the pass flag and its notes; the regression harness compares the file with a git tag and fails on any other edit. New ideas go to a separate proposals file for me to accept.
- **One feature at a time**, each behind an automated regression gate, with a fuller gate at the end of each milestone.
- **A fresh-context evaluator at every milestone**, because, as the roadmap puts it, agents over-praise their own work. The evaluators do fail work: the open-world vertical slice failed four rounds on water and terrain seams before it passed on the fifth, graded by a panel of two.
- **Playtest stops** at six points where feel matters more than any test. The agent merges, writes a checklist, and waits for me.
- **A paper trail:** an append-only session log, numbered decision records, and numbered open questions for me to answer.

**Multi-agent workflows with critics.** For the newest content work, each map has its own workflow: a plan, a builder for the look, a builder for the roads, a code review and a critic, then a fix pass. Planning and critique run on a different model from the builders, and an adversarial verifier caught a fix that had not fully closed a water bug. My part in this phase is direction: feedback on the look, reference photos, and the calls recorded as decisions.

An agent can’t see the screen, so the game has tooling built for one: named camera shots for every level, an autopilot that drives any route and reports JSON, a runner that fails on any script error, golden-image comparisons, and a machine-wide lock so only one run uses the GPU at a time. It is the same approach as my [agent toolkit at work](/work/agent-toolkit/): written rules, scripts for anything that must be repeatable, and a person deciding what counts as done.

## No asset files, and a cache keyed by its own source code

The repository has no imported models, textures or audio. Meshes are built vertex by vertex, textures are generated images, and every sound is synthesised, including the engine, which is modelled from the crankshaft’s rotation on a worker thread.

Generating a level is deterministic but not instant, so the result is cached on disk. The cache key is a hash over the engine version, the level’s seed and **the source text of every generator script the level uses**, followed transitively, with comments excluded. Any code change invalidates exactly the entries it affects, with no version numbers to bump by hand. Writes are atomic, large arrays are compressed on worker threads, and a verify flag regenerates a level and compares it byte for byte.

One consequence became a written rule: open-world classes can’t have generic names like `Trail`. The key follows every capitalised word that names a global class, so a generic name would quietly pull open-world code into the timed levels’ cache keys.

## Vehicle physics from scratch, tested by a bot that types

The truck is one rigid body in Jolt Physics, stepped 120 times a second. Everything else is custom GDScript rather than Godot’s built-in vehicle:

- a shape cast per wheel, so large tires roll up rock edges instead of snagging on them;
- progressive springs and bump stops on a solid rear axle;
- a brush tire model with a friction circle and load sensitivity, and loose ground that digs in;
- a drivetrain with a torque curve, torque converter, automatic gearbox, high and low range and lockable differentials, solved four times per physics step.

The HUD shows a tip margin, the degrees left before the truck rolls, computed from its support polygon and the effective gravity on it.

Metric tests were not enough to judge feel. A test bench runs scripted experiments side by side and prints a pass/fail table, and a keyboard bot presses W, A, S and D on a timeline through the same input shaping a player gets. The bot found problems the metric tests had missed: short taps of the throttle did nothing on hills, handbrake turns did nothing with the centre differential locked, reverse was far too fast, and every jump over a crest raised a false rollover warning.

## The real truck

The truck in the game is loosely based on my own: an old 4Runner I’ve been building up and taking out on trails in Colorado. Picking a line over a rock, easing across a log and stopping at the top for the view are the parts of those trips I wanted the game to get right.
